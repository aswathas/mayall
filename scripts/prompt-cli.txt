# WHAT TO BUILD

## 1. contracts/test/LongSession.t.sol — THE 200-TRANSACTION HAYSTACK
A Foundry test that performs ~200 transactions inside ONE test run, with a real
attack hidden among benign ones.

- `src/SessionVault.sol`: a benign multi-user vault (deposit / withdraw / a
  simple share accounting) — normal traffic.
- `src/SessionNoise.sol`: a benign counter/escrow used for filler transactions.
- `src/SessionVault.sol` must ALSO contain the vulnerable withdrawal path (the
  same checks-effects-interactions flaw as ReentrancyVault) so the attack can
  be committed inside the session.
- The test:
  - runs N (default 200) top-level transactions from the test contract:
    deposits, withdrawals, noise calls, transfers — mostly benign;
  - at a configurable index (default 137) it executes the real re-entrancy
    attack against the session vault;
  - records the index of the attack transaction in the artifact;
  - writes a structured artifact to $HELIX_ARTIFACT_DIR/long-session.json with
    the SAME schema as the other PoCs (scenario: "long-session", attackVector:
    "Reentrancy", chain: "Ethereum", steps, balances, storageWrites, logs) PLUS
    two extra fields: "txCount" (number of transactions) and "attackTxIndex".
- The attack must genuinely drain value and the test must assert it.

## 2. packages/forensic-engine/src/session.ts — SEGMENT AND TRIAGE
The analysis the CLI needs:
- `segmentTransactions(trace: TraceNode | null): Transaction[]`
  A Transaction is one TOP-LEVEL call made by the test contract, with its
  subtree, its gas, its value and its index.
  The root trace node is the test function; its children are the top-level
  transactions (plus harness noise — VM:: cheatcode calls are NOT transactions;
  filter them out).
- `analyseSession(trace, artifact): SessionAnalysis`
  For EACH transaction: run the existing detectors over that transaction's
  subtree (reuse runDetectors with a per-transaction context) and score it.
  A transaction is SUSPICIOUS when it (a) produced pattern findings above the
  confidence floor, or (b) shows a repeated (contract, function) pair nested
  within itself, or (c) moved value out of a victim contract.
- Return: { transactions: Transaction[], suspicious: { index, reasons, confidence }[], cleanCount }
- The point of the feature: with 200 transactions and one attack, the analysis
  must isolate the attack. Assert this in the CLI's own run output and in a
  self-check.

## 3. packages/forensic-engine/src/plan.ts — THE CLIENT PLAN
`buildClientPlan(analysis, report): ClientPlan` producing the artefact a
client actually acts on. It must be plain language, not JSON jargon:
- **Where the flaw was** — the exact contract and function, the file if known
  from the trace, the line of behaviour that is wrong ("the state update happens
  after the external call in withdraw()").
- **Why it was exploitable** — the precondition that made the attack possible.
- **What it cost** — the loss figure, in the asset and in USD where known.
- **What to do Monday morning** — a short, ordered, concrete list: the
  immediate containment step, the one-line code fix, the verification test to
  write, and what to check in the logs for historical exposure.
- **What is still unknown** — the honest gaps (e.g. this is a local
  reproduction; it does not prove the live deployment was exploited).
Render it as Markdown.
