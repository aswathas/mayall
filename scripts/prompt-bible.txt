## app/bible/page.tsx — THE INDEX
The Forensic Bible index. It must read like a reference work, not a landing page.
- A real <h1> ("The Forensic Bible" or similar). No kicker above it.
- A one-paragraph orientation: what this is, in plain words, and the honest
  statement that the rules below are the rules the engine actually executes.
- A compact metric strip: 16 attack vectors, 10 detectors, 6 live
  reproductions, and the number of vectors that currently have a local proof.
- The vector list: a dense, scannable index (NOT a grid of identical cards).
  Use a table-like or definition-list layout: vector name, category, severity
  weight, which detectors watch for it, and a LIVE badge where a reproduction
  exists. Each row links to /bible/<vectorId>.
  Make the layout feel like an index in a serious reference book — dense,
  aligned, with hairlines, and it must fill the page without dead space.
- Group the list by category (Value Extraction, Access & Control,
  Oracle & Market, Logic & Math, Infrastructure) with the category as a
  section heading. The grouping carries information, so it earns its headings.
- A short "how to read this" block explaining the three things a vector entry
  gives you: the pattern, the trace signature, and the fix.

## app/bible/[vectorId]/page.tsx — THE ENTRY
A deep entry for one attack vector. This is the page that has to teach.
- Header: vector name (h1), category, severity weight, and a LIVE badge plus
  a "Reproduce locally" button when a scenario exists (linking to
  /lab?scenario=<scenario.id>).
- **What the pattern is** — the vector's `signature` plus a short, precise
  explanation of the mechanism in plain language. Two or three sentences that
  a protocol engineer would find accurate, not marketing copy.
- **The trace signature** — what you see in a call tree when this attack fires.
  Be concrete: which function repeats, which storage slot moves, which balance
  moves. Where a live scenario exists, use its `lookFor` checklist as the
  signature.
- **The detectors** — every detector in DETECTOR_CATALOG that watches for this
  vector: its label, its base severity, exactly what it looks for (`looksFor`),
  the evidence it emits (`emits`), and its honest limitation. Present the
  limitation clearly, not hidden in a tooltip.
- **The fix** — the remediation for this vector, in code terms. Write it from
  the mechanism: what to reorder, what to guard, what to bind. Concrete enough
  to act on.
- **Evidence from our lab** — when a live reproduction exists, show the real
  measured figures from the local run (the loss in ETH and the confidence the
  detector reached). These are real numbers from our lab; they must be
  accurate. The numbers live in the artifacts on disk
  (C:\Users\aswat\Projects\w3-forensics\artifacts\<scenario>.json) — read them
  at build time in the server component if you want them exact, or state them
  with the scenario's description. Do NOT invent figures that contradict the
  artifacts: reentrancy 6 ETH, oracle-manipulation 40 ETH, access-control
  50 ETH, flash-loan 250 ETH, delegatecall 50 ETH, selfdestruct 60 ETH.
- An "all vectors" link back to the index.
- Not-found handling for an unknown vectorId: a real empty state.
