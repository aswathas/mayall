## WHAT TO BUILD

### 1. A REAL, PARAMETERISED Foundry attack (the core of this brief)
`contracts/src/CustomTarget.sol` — a deliberately vulnerable vault that supports the attack families
that make sense in one contract:
  - reentrancy (withdraw sends ETH before zeroing the balance)
  - access control (an `owner`-gated `drain()` with a predictable/compromisable owner, plus a
    `tx.origin` style flaw)
  - oracle manipulation (a price oracle that trusts an LP-reserve-derived spot price with no TWAP)
  - flash loan (borrow/settle in one transaction, no economic check)
  - delegatecall injection (a proxy pointing at an attacker-controlled implementation)
  - selfdestruct (a destroyable target whose funds go to the attacker)
Keep ONE contract with switchable behaviour driven by an enum, so a single Foundry test can simulate
every family against it. Add `contracts/src/CustomNoise.sol` — benign traffic contracts used to pad a
session with realistic noise transactions so the trace has depth.

`contracts/test/CustomAttack.t.sol` — ONE Foundry test named `testCustomAttack` that:
  - reads its configuration from environment variables so the same test binary can be re-run with
    different parameters:
      `MAYALL_VECTOR`   (one of: reentrancy, access-control, oracle-manipulation, flash-loan, delegatecall, selfdestruct)
      `MAYALL_TXS`      (integer, number of attacker transactions to execute — default 3)
      `MAYALL_AMOUNT`   (integer, total wei to drain — default 6 ether)
      `MAYALL_SEED`     (integer, noise seed — default 1)
    Use `vm.envOr("MAYALL_VECTOR", string("reentrancy"))` etc. so the test still runs with no env set.
  - executes `MAYALL_TXS` attack transactions (loop) against the target, interleaving benign noise
    activity so the trace has multiple top-level calls, and asserts a REAL invariant, e.g.
    `attackerGain == expectedDrain` and `targetDeficit > 0`. The assertion must be a genuine
    property of the scenario, not a tautology.
  - writes the same artifact JSON shape that `ExploitBase.t.sol` writes (read that file and reuse its
    builder helpers — import from `test/ExploitBase.t.sol`), into the artifact directory so the
    TypeScript engine can read it. Use the same env var the existing harness uses for the output
    directory (read `ExploitBase.t.sol` to find it; if it is not env-driven, use
    `vm.envOr("HELIX_ARTIFACT_DIR", string("./artifacts"))` semantics and make the path match what
    `packages/forensic-engine/src/foundry.ts` expects).
  - MUST PASS. Verify by running forge yourself (see the Foundry invocation below).

### 3. API routes
- `GET  /api/custom/options` → the vector catalogue + parameter bounds + the toolchain status.
- `POST /api/custom` → body `{ vector, txs, amountWei, seed }`; runs the simulation and returns
  `{ caseId, artifact, detections, report, traceSummary, bundleUrl }`. `caseId` should be
  `custom-<vector>-<timestamp>`; the artifact/report should be persisted under the artifact dir so the
  report route and bundle route can serve it by id. Keep it consistent with how `/api/simulate` and
  `/api/report/[caseId]` already work — read those files first and follow the same conventions.
- `GET  /api/custom/stream?vector=&txs=&amountWei=&seed=` → **Server-Sent Events**. This is the LIVE
  RUN. It must spawn `forge test --match-path test/CustomAttack.t.sol --match-test testCustomAttack -vvvv`
  as a child process, pipe stdout LINE BY LINE, and push each line to the client as an SSE `data:` event
  (plus periodic `progress` events with the current forge output). It must emit a terminal `done` event
  with the caseId and the bundle/report URLs, and an `error` event on failure. Set
  `export const dynamic = 'force-dynamic'` and `export const runtime = 'nodejs'`.
